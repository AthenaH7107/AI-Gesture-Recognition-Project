# AI-Gesture-Recognition-Project
## Description
This project implements a gesture-controlled code guessing game using two ESP32-C6, an inertial measurement unit (IMU), pushbuttons, and a graphical display. The system allows the user to input directional gestures (including up, down, left, and right) using physical motion, which will then be classified using an embedded machine learning model and transmitted wirelessly to the receiver device to be displayed.
## Project Components
The project includes four different parts: ESP32-C6, LCM sensor, push buttons, and uLCD Display. The ESP32-C6 processes data collected from the LCM sensor and responses from the pushbuttons, runs the control logic as well as the ML inference, and finally sends information to be displayed on the uLCD. Because I have used two ESP32s for this project, I have designed one to be the receiver, which is responsible for data collection (from the sensor and buttons) and data processing (running the ML model to predict the result), and the other one as the sender to display the answer and current/confirmed codes. As mentioned above, the LCM 9DS0 sensor is an IMU sensor that combines a 3-axis accelerometer, 3-axis gyroscope, and 3-axis magnetometer. In my project, I am responsible for collecting real-time 3-axis accelerometer and 3-axis gyroscope data to be sent to the ESP32 and finally processed by the machine learning model. There are three buttons designed for the project: the Guess Button is to notify the ESP32 to start collecting data to be sent to the ML model to be analyzed; the Confirm Button sends the result that the user is satisfied with to the display module and gets recorded for the final answer check; and the Send Button informs the ESP32 that the user is done with all the confirmed guesses and would like to have their answers checked. The display module is responsible for communicating the results to the user, apart from the serial monitor. It displays the answer codes in white triangles, the current guesses with blue triangles, and confirmed ones with green triangles. It will display a green circle for a win and a red circle for a loss.
## More Detailed Program Flow
As mentioned above, the system is divided into two main components: the sender ESP32 and the receiver ESP32. The sender ESP32 is responsible for the collection of motion data from the IMU sensor (specifically the LSM9DS0), processing the data, running the on-device machine learning model generated with Edge Impulse, and finally sending the guesses. The receiver ESP32 is the game controller and display interface.
Upon the start of the game, the receiver ESP32 generates a random sequence of directional gestures (up, down, left, and right) that serves as the “code” that the user must enter and will be printed on the screen, represented by isosceles triangles pointing in different directions. When the user presses the “guess button”, the system starts recording the 3-axis accelerometer and 3-axis gyroscope data over a short time period. This data is passed into the machine learning classifier, which predicts the gesture being performed. The result is then transmitted wirelessly using the ESP-NOW protocol. The receiver then displays the received “predicted guess” in blue triangles under the white triangle codes, and these current guesses can be updated through pressing the guess button again if the user is unsatisfied with their previous motion or the model’s prediction. If the confirm button is pressed, the microcontrollers will lock the predicted gesture as part of the user’s final answer and move on to the next index. The confirmed guesses will be represented by green triangles. The user can repeat the guess and confirm steps until they are satisfied with their input sequence. They can then press the send button that will submit the full sequence of gestures as a final answer to the receiver ESP32, which will compare the guessed sequence to the generated code. The final result will be displayed visually: a green circle indicates a correct solution, while a red circle indicates an incorrect guess.
## Problems
The most significant challenge that I have encountered in the project is training the Machine Learning model. I trained my machine learning model three times for better accuracy. The first time, I was only able to get a 60% accuracy rate with 10 min of data for the five gestures in total. I later figured that it was because I added too much variation that it turned out to be inaccurate from the data collection stage, since the very beginning. For example, if I do “left” facing north and then “left” facing south as well, the LSM is going to recognize them as opposite directions since it wasn’t able to capture the actual direction. So I re-did my data collection stage, this time only facing one direction. I was able to get a slightly better overall result this time, but I consulted a friend who has more experience training ML, and they said that I should add fewer “tilt” variations and keep the model as stable as possible. So I re-collected my data once again, this time finally obtaining an overall score of greater than 80% and, with the only exception of “left” motion being 60%. However, after deploying, the model was still underperforming, which led me to cancel the original project plan that involved accurately entering the gesture within a timing constraint.
## Real-World Application
I was inspired by the dance arcade games where players step on the different tiles on the ground to match the music and patterns on screen, which is also an embedded system. My project is a simplified arcade graphical version of it, but with the addition of the ML model to predict the users’ motions based on sensor-collected data. Specifically, it is similar to the dance arcade game in that it includes four different directions, as well as the idle mode (when you don’t enter anything) that needs to be sent to the machine for interpretation. It includes sensor gathering data, though I am implementing the LCM sensor so the ML model can predict the movement according to users’ motions, while the dance game uses a more direct touch-based sensor. But they both include some sort of analytical and display features – to run the game, decide whether the player’s input is correct, and finally display results.
## Future Improvement
There are two things that I am not fully satisfied with: one is the accuracy of the machine learning model, and the other is the graphical content. If given the time, instead of training the model to recognize one single gesture at a time, I will instead train the model with a sequence of gestures as combinations of directional gestures. Apparently, machine learning is better at reading these more complicated motions than, say, a single upward motion. While this means that I will need to change my game logic a little bit, I think I will have a great time training the model and playing around with the more complicated features with better accuracy. On the other hand, with the (hopefully) increased ML prediction accuracy, I would add to the graphical content rather than simple triangles. To better resemble the dance arcade game, it would be more fun if the sequence of gestures moves down slowly from the top of the screen and takes players’ time off if still not entered when it touches the bottom of the screen – that is, adding a time limit to each guess as well as the scoring system. I think these improvements together will be able to make this project more sophisticated and enjoyable.
